# Stripe Sandbox Setup

This guide connects the standalone payment POC to Stripe without moving real money. The local payment database, RabbitMQ, and demo consumer can already be tested without Stripe credentials using `node scripts/local.mjs test-infra` from the payment-service directory.

## Safety First

- Sign in and enter credentials yourself. Do not share passwords, OTPs, API keys, signing secrets, or screenshots containing them in chat.
- Use a dedicated sandbox and test cards only. Never use `--live`, `sk_live_` keys, actual card numbers, bank details, or real payment methods for this POC.
- Use truthful account/country details. Sandbox access is not proof of eligibility for a live merchant account or USD settlement in Cameroon. If account setup blocks sandbox access, stop and check Stripe support rather than claiming another country.
- The startup guards accept sandbox secret-key families `sk_test_`, `rk_test_`, and `rkcs_test_`, and reject live/publishable keys. A matching prefix is not proof that a key is valid or has sufficient permissions: Stripe must authorize session creation/retrieval, and the service still checks provider objects/events for sandbox mode. Restricted keys need the permissions required by Checkout; use least privilege and never production credentials.
- If any secret was included in a chat attachment or screenshot, treat it as exposed and replace/revoke it privately before further use. Never attach this project's private environment file. Local database/broker password changes must be coordinated with existing volumes; rerunning `init` preserves credentials and is not rotation.

## 1. Create or Select a Sandbox

### Temporary CLI Sandbox

If you already ran `stripe sandbox create --email YOUR_EMAIL_ADDRESS` successfully, your CLI has saved that temporary sandbox context. Keep it selected; do not run `stripe login` merely to start webhook forwarding. Enter its `rkcs_test_` secret directly into the payment environment file, then continue with step 4 below.

Stripe documents temporary sandboxes as expiring after seven days unless claimed. Respect the expiry reported by your CLI and treat the claim URL as sensitive. Claiming/account setup can still have country/eligibility requirements; temporary sandbox access is not a live-account workaround. A fresh sandbox has different keys and session objects, so use new synthetic order references after switching environments.

### Create Local Temporary Credentials

Run the following yourself in an unshared terminal because creation prints a secret key and claim URL. The email placeholder must be replaced with your actual email; it is not a key:

```sh
npm install -g @stripe/cli
stripe version
stripe sandbox create --help
stripe sandbox create --email YOUR_EMAIL_ADDRESS
```

If the CLI is already installed, skip installation. The temporary flow applies when the CLI is not authenticated to an existing account; an authenticated CLI can open sandbox management in the Dashboard instead. Do not run a new creation command while a valid sandbox is already serving your current demo.

Record the returned sandbox/account identifier and exact `expires_at` date privately. These credentials are issued by Stripe, not generated by `node scripts/local.mjs init`. The local helper generates only database, RabbitMQ, and demo JWT secrets. Seven days is a sandbox lifetime, not an automatic rolling renewal of the same key.

After creating the sandbox:

1. Enter its sandbox secret directly into `STRIPE_SECRET_KEY` in the ignored payment environment file.
2. Run the listener in step 4 and enter its signing secret into `STRIPE_WEBHOOK_SECRET`.
3. Keep that listener and sandbox context active, then recreate the Payments container using the startup command below.

### Before or After the Seven-Day Expiry

Choose either to claim the sandbox through Stripe's legitimate account flow or to replace it for another temporary demonstration. `stripe sandbox claim` opens the claim flow; it does not promise live merchant support or bypass country restrictions. Never share its claim URL.

To replace a temporary sandbox:

1. Finish current tests and stop its `stripe listen` process with Ctrl+C. Record which synthetic payments belong to this sandbox.
2. Follow the installed CLI's `stripe sandbox create --help` instructions to create a new temporary environment. If your CLI instead opens the Dashboard because it still has an authenticated context, inspect `stripe logout --help` and sign out deliberately before creating the replacement. Logout changes your local CLI context and must not be assumed to revoke the old API key or extend its lifetime. Do not sign out of another project's account unintentionally.
3. Enter the new sandbox key directly in `STRIPE_SECRET_KEY`. Restart the listener in the new sandbox and enter the signing secret it reports in `STRIPE_WEBHOOK_SECRET`.
4. Recreate the Payments container through the helper or full-stack command. A running container does not reread edits to an environment file.
5. Use a fresh synthetic order reference for the new sandbox. Old Stripe session IDs are not available with the new environment's credentials. Never reuse an old pending payment as evidence of a new payment or silently mark it failed/paid.

Do not change database/RabbitMQ credentials merely because a Stripe sandbox expires, and do not delete volumes to renew a Stripe key. Existing pending sessions from an expired sandbox remain unresolved local records and may produce reconciliation warnings. For this small demo, preserve them for inspection and avoid accumulating more than the worker's 20-row reconciliation batch; administrative archival and multi-environment reconciliation remain future hardening. Terminal results/outbox history do not need deleting to test a new reference.

If a key was exposed before expiry, replace/revoke the exposed credentials immediately using Stripe's supported controls rather than waiting seven days. Temporary-environment deletion/replacement and credential revocation are distinct operations; verify what Stripe actually revokes.

### Dashboard Sandbox

1. Open the [Stripe Dashboard](https://dashboard.stripe.com/) and sign in, or create your account directly in the browser. Complete any email/2FA steps privately. Do not activate live payments for this demo.
2. Open the account picker, then **Switch to sandbox > Create sandbox**. Some Dashboard layouts show **Sandboxes** first.
3. Name it `ember-bean-local`.
4. Choose **Create an account from scratch** for an isolated environment rather than copying an existing account's settings, then create the sandbox.
5. Open that sandbox and verify the sandbox banner before generating keys or making API calls.

You need an appropriate account role to create a sandbox. If the option is missing, check the account/role and Stripe's current onboarding requirements. Do not use live mode to work around missing sandbox access.

## 2. Store the Sandbox API Key

Inside `ember-bean-local`, open **Developers/Workbench > API keys**, or navigate to the [API keys page](https://dashboard.stripe.com/apikeys) and recheck that the selected environment is your sandbox.

Reveal/create the appropriate sandbox secret key, or use the key from your temporary CLI sandbox, and enter it directly into the ignored [payment-service/.env](../.env) file's `STRIPE_SECRET_KEY` entry. Never copy it into the tracked `.env.example` or the repository-root coffee configuration. Do not reveal the key in an assistant-controlled/shared browser snapshot.

| Value | Prefix | Used by this POC |
| --- | --- | --- |
| Standard sandbox secret API key | `sk_test_` | Payments creates/retrieves Checkout Sessions |
| Restricted sandbox secret API key | `rk_test_` | Same API calls, subject to granted permissions |
| Temporary CLI sandbox secret key | `rkcs_test_` | Same API calls, subject to temporary sandbox permissions/expiry |
| Publishable API key | `pk_test_` | Not needed; no Stripe.js or Elements integration |
| Webhook signing secret | `whsec_` | Receiver verifies a webhook; obtain from the CLI listener below |

If the payment `.env` does not exist, initialize it from the repository root:

```sh
node payment-service/scripts/local.mjs init
```

Initialization preserves existing values and creates random local database/broker/JWT credentials with mode 600. Do not replace those credentials while initialized database/broker volumes still use their old passwords.

## 3. Install and Authenticate Stripe CLI

On macOS with Homebrew, run these commands in your own terminal:

```sh
brew install stripe/stripe-cli/stripe
stripe version
stripe login
```

The login command is for the Dashboard-account route. If a temporary CLI sandbox is already active, skip login and proceed directly to `stripe listen`. It is normal not to need Dashboard registration for that temporary flow.

Use the browser-based pairing flow, verify the code shown by your terminal, and authorize **the same `ember-bean-local` sandbox** as the API key. Do not put a secret key in a command-line flag or shell history. Current CLI versions may require enabling CLI access under **Settings > Team and security > MCP and CLI access** for that environment.

If the installed CLI supports them, `stripe login list` and `stripe switch` let you inspect/select authorized sandbox context. On older CLI versions, use the browser login selection for the correct sandbox; consult `stripe login --help` before following version-specific flags. Do not use `stripe config --list` in shared output because some versions can print keys.

## 4. Forward Local Webhooks

In a dedicated terminal, run:

```sh
stripe listen --events checkout.session.completed,checkout.session.expired --forward-to http://localhost:18081/webhooks/stripe
```

The CLI prints its `whsec_` signing secret. Enter that value directly into `STRIPE_WEBHOOK_SECRET` in the payment-service `.env`, without sending it to chat. Keep the listener running while testing. If the service is not running yet, start it in the next step after setting this secret.

This local listener does not require creating a public webhook endpoint in the Dashboard or exposing localhost to the internet. Its signing secret is not the API key and is not interchangeable with a Dashboard endpoint's secret. When a listener/environment changes, use the secret shown by that listener and recreate the payment container if its configuration changes.

`STRIPE_WEBHOOK_SECRET` holds the `whsec_` value, not a URL. The local receiver URL is `http://localhost:18081/webhooks/stripe`, which is passed to the CLI's `--forward-to` flag.

## 5. Start and Create a Payment

From the repository root, in another terminal:

```sh
node payment-service/scripts/local.mjs up
node payment-service/scripts/local.mjs checkout demo-order-1 300
```

The helper verifies/packages the JAR, then uses the root Compose file to start Payments, RabbitMQ, its databases, and the demo consumer. It does not change the coffee backend's checkout. The command returns a payment ID, `PENDING` status, and provider-created Checkout URL. `300` means USD 3.00, not USD 300.

Open the Checkout URL yourself and use Stripe's documented sandbox card `4242 4242 4242 4242`, any future expiry, and any three-digit test CVC. Fill other requested fields with non-sensitive test details. Never enter a real card number. To demonstrate a generic decline, Stripe documents `4000 0000 0000 0002`; confirm the current scenarios in the [test-card reference](https://docs.stripe.com/testing#cards).

Then read the status using the returned payment ID:

```sh
node payment-service/scripts/local.mjs status PAYMENT_ID
```

A successful flow becomes `SUCCEEDED` after signature/provider verification, then reaches the demo consumer through the outbox and RabbitMQ. It is normal to briefly see `PENDING`; background workers run at intervals. The browser return page itself never confirms payment. For another demonstration use a new synthetic order reference; identical retries reuse the original attempt.

## 6. Start All Services and Test Together

All commands in this section run from the repository root. Keep the Stripe listener in a separate terminal; do not start a second listener with a different sandbox/secret accidentally.

### Full Stack Startup

```sh
mvn -f backend/pom.xml --batch-mode --no-transfer-progress package -DskipTests
mvn -f payment-service/pom.xml --batch-mode --no-transfer-progress verify
KEYCLOAK_ENABLED=true docker compose --env-file .env --env-file payment-service/.env --profile sso --profile payments up -d --build
docker compose --env-file .env --env-file payment-service/.env --profile sso --profile payments ps
```

The two environment files are private coffee/SSO and payment settings. Neither is committed. This starts the existing app and SSO alongside Payments, RabbitMQ, and the isolated consumer, without resetting volumes. `KEYCLOAK_ENABLED=true` enables backend SSO explicitly; the `sso` profile alone only starts the provider containers. If the login button is disabled, check `/api/v1/auth/providers` for `keycloak: true` before debugging the frontend. Runtime images use the prebuilt JARs. Backend packaging above skips tests for startup convenience; its verification command remains `mvn -f backend/pom.xml test`.

| Service | Local URL | Check |
| --- | --- | --- |
| Coffee UI | `http://localhost:8088` | Browse, sign in, place a coffee order |
| Coffee backend | `http://localhost:18080/actuator/health` | `UP` |
| Payments API | `http://localhost:18081/actuator/health` | `UP`; private endpoints still need JWTs |
| Demo consumer | `http://localhost:18082/actuator/health` | `UP`; no customer-facing order UI |
| Keycloak | `http://localhost:8180/realms/coffee-shop/.well-known/openid-configuration` | Realm metadata responds |
| Mailpit | `http://localhost:8025` | Captured local registration/order emails |
| RabbitMQ management | `http://localhost:15674` | Use the local generated broker credentials privately |

### Manual Test Checklist

1. Open the coffee UI and verify sign-in/catalog/orders independently. Creating a coffee order still does not request payment; business integration is future work. Local emails appear in Mailpit, not an external inbox.
2. Confirm your Stripe listener is active and uses the current sandbox and configured webhook secret.
3. Create a synthetic USD 3.00 payment using a fresh reference:

```sh
node payment-service/scripts/local.mjs checkout "sandbox-$(date +%s)" 300
```

4. Record the returned payment ID and open the returned Stripe Checkout URL privately. Use the successful test card from step 5 and complete payment. Never use real cards.
5. Check that the listener receives `checkout.session.completed` and the receiver returns 204. The API can remain `PENDING` briefly while the worker verifies provider status. Query using your recorded ID:

```sh
node payment-service/scripts/local.mjs status PAYMENT_ID
```

6. Expect `SUCCEEDED`. Inspect the outbox and demo consumer's database separately:

```sh
docker compose --profile payments exec -T payments-db psql -U payments -d payments -c 'SELECT event_id,payment_id,published FROM payment_outbox ORDER BY created_at DESC LIMIT 5;'
docker compose --profile payments exec -T demo-db psql -U demo_orders -d demo_orders -c 'TABLE demo_orders;'
```

The matching event should become `published=true`, and the synthetic order should show `PREPARATION_ALLOWED`. That flag belongs to the demo database only; it does not change a coffee order. A drained RabbitMQ queue is normal when a healthy consumer processes immediately.

7. Repeat the exact create command with the same order reference and amount to check idempotency: it must reuse the attempt. Change the amount with the same reference to observe 409. Use a new reference for a declined-card or browser-cancel test; both remain unpaid until actual provider state establishes paid or expired.
8. For queue observation, stop only `demo-consumer`, complete another synthetic sandbox payment, inspect `demo.orders.payments` depth in RabbitMQ, then restart the consumer. Messages should drain and appear in its database. Use `docker compose --profile payments stop demo-consumer` and `docker compose --profile payments start demo-consumer`; do not stop/delete the databases for this exercise.

To run automated infrastructure verification, prefer stopping the interactive consumer first so the test listener is the only consumer during the run, then restart it afterward:

```sh
docker compose --profile payments stop demo-consumer
node --test payment-service/scripts/sandbox-key.test.mjs
node payment-service/scripts/local.mjs test-infra
docker compose --profile payments start demo-consumer
```

Infrastructure tests use real local databases/broker but mock Stripe; they do not prove that the current sandbox key is valid. They add synthetic records and deliberately send malformed messages to test dead-lettering. Do not run them against production databases or a production broker.

`node payment-service/scripts/local.mjs down` stops only the payment stack. To stop everything intentionally, use the full root Compose command with both environment files/profiles and `down`, without `--volumes` unless you explicitly want to erase data.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Startup rejects the API key | Use a valid sandbox secret key with `sk_test_`, `rk_test_`, or `rkcs_test_` and a nonempty value; no live keys, publishable keys, whitespace, or placeholders |
| Stripe rejects a restricted/temporary key | Check actual Checkout permissions, key revocation, sandbox context, and temporary sandbox expiry; do not bypass rejection with a live key |
| Invalid webhook signature | Use the running CLI listener's secret, preserve raw requests, and check the machine clock |
| No local webhook | Keep the listener running, select the same sandbox as the API key, and confirm port 18081 is reachable |
| 204 received but payment still pending | Check worker/provider verification; receipt alone does not prove payment |
| Provider session not found | API key and CLI may refer to different sandbox accounts, or the configured key was rotated |
| Container still uses an old secret | Save the private file, then rerun the `up` helper to recreate the affected service |
| Generic CLI trigger produces no paid order | A fixture session has no matching local attempt/reference; complete the Checkout Session created by our API instead |
| Duplicate checkout returns 409 | Reuse the same order/amount/key for a retry, or choose a new synthetic order for a new demo |

Do not troubleshoot by printing the `.env`, API key, signing secret, JWT, or full resolved `docker compose config` into shared logs. Rotate any secret accidentally exposed. For safe queue/database inspection and failure exercises, see [communication.md](communication.md).
